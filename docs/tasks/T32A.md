## 范围和实现

- 手机「实战 → 我上头了」直接记录；首次说明用途、180 天保留期及可提前删除，明确同意才调用 T05 `setConsent(manual_mark)`。选择「暂不记录」不授权、不创建。「实战 / 成长 → 标记历史」只读，可翻页、补或清除对象/场景、删除、写复盘。
- 服务端 `internal/marks` + `internal/service/marks_http.go` 实现 T03 四个 marks operation。T05 `WithSession` 在业务事务内锁账号、复核会话/冻结/删除屏障；写入再检查当前 `manual_mark` 同意。撤回后仍可查、导出及删除。
- 锁内先查删除墓碑；未删除的旧 request ID 返回原记录。新键再按服务端受理时间比较上一条新建：`<60s` 只增加请求映射，恰满 `60s` 可新建；无论哪个键，成功重试都回到原条目，不更新时间。数据库 UTC 半开区间排斥约束兜住并发。
- 加密沿用 T25 的 `mark/<user UUID>/<mark UUID>` AAD；时间、场景来自密文，对象归属来自复合外键。`accepted_at` 仅用于滚动窗口、稳定游标和 180×24h 到期判定；到期即排除读取/导出，分钟任务走 T04 协调器物理清理。
- `manual_marks.json` 流式导出当前账号有效标记，不含请求映射或墓碑。单条、关系人级联、180 天清理和账号删除均覆盖相关数据。
- `app/lib/features/marks/` 的复盘跳转传 `mark_id`、`occurred_at`、可选 `contact_id` / `scene`。首轮交付时 `/marks/review` 只是复盘起点页；T24 合入后该路由直接打开正式 `ReviewPage`，预填随 T16 账号隔离的加密本机草稿保存，并由页面提交复盘。

## 第二轮阻断的复现与修复

### 1. 删除后延迟重放不能重建已删对象

**复现。** 修复前删除标记会级联清除 `mark_requests`；等待超过 60 秒后再次提交原 request ID，`Create` 进入新建分支并返回 200。反例副本只移除 `Create` 的墓碑查询，真实 PGlite/Gin 测试输出 `marks_integration_test.go:234: POST marks: HTTP 200 want 409`。旧 Widget 的“刷新后按时间清 pending”也不能证明哪个请求已提交，因此没有覆盖原键重放。

**修复。**

- 新迁移 `20261122001532_manual_mark_tombstones` 增加 `manual_mark_tombstones(user_id uuid, request_id uuid)`，主键 `(user_id, request_id)`，用户外键 `ON DELETE CASCADE`。表中没有标记 ID、标记/删除时间、对象、场景、密文或其他个人内容。
- 证据边界：`user_id` 只提供账号作用域，`request_id` 是客户端随机不透明请求键；两者组合与仓库既有 T23 `review_tombstones` 的账号内请求键模式一致，不是可展示或可检索的标记内容。T04 Redis `deleted:<opaque_id>` 只登记已删除源，不能替代“同账号原 request ID 已删除”的冲突判定，因此这里不能改用无账号作用域的源删除登记。
- `BEFORE DELETE ON manual_marks` 在级联清除 `mark_requests` 前，把该标记关联的全部请求键复制为墓碑；覆盖单条删除、关系人级联、180 天清理和账号清除。账号已被删除时不插入墓碑，最终随用户级联清零。
- `marks.Service.Create` 在 consent 后先查墓碑；命中原键返回 `ErrDeleted`，绝不进入新建或 60 秒复用分支。HTTP 映射为 `409 conflict`、`retryable=false`，文案“这次标记已删除，请重新记录”。
- App 遇到 409 清除 pending，不显示成功；下一次点击生成新 request ID。其他失败保留原 ID，以便丢响应后由服务端按原键返回原记录。历史刷新不再用时间近似清 pending，必须原键重试或收到 409 后才结束本地意图。
- 回归覆盖：删除后立即及模拟 61 秒后重放均 409、`manual_marks` 保持 0、墓碑存在且列严格只有 `request_id,user_id`；新键可正常创建；关系人级联生成墓碑；账号清除后墓碑为 0；删除触发器模拟失败时 DELETE 500，标记仍在且墓碑不存在；原 `<59.999999s` 复用和恰满 `60s` 新建断言继续通过。

### 2. 短暂删除屏障不得冒充登录失效或清空本机草稿

**复现。** 删除待办已提交、独立登记暂不可用时，历史请求返回 `privacy.ErrHidden`；旧 `accountError` 将其映射为 401。App 随后自动刷新，刷新也被同一屏障拒绝为 401，于是 `Sessions.clear()` 销毁本机密钥并删除缓存目录，服务恢复后也无法找回草稿。旧首轮实现的回归反例输出 `marks_barrier_test.go:19: pending barrier status = 401, want 503`。

**修复。** `privacy.ErrHidden` 统一映射为 `503 service_unavailable`、`retryable=true`；只有 `accounts.IsAuth` 仍是 401。历史读取和 `POST /v1/auth/refresh` 都保留会话与本机草稿，不报告删除成功。Widget 覆盖刷新遇可重试 503 时会话和草稿仍在；删除失败不显示“标记已删除”、不移除卡片；首次取消/失败不显示“已记下”。

## 第三轮复审窄修复

### 1. 到期但清扫前重放原 request_id 不得新建

**反例。** 标记恰好满 180 天、历史读取已将其排除，但分钟清扫尚未删除真实行时，旧 `Create` 会主动移除请求映射并继续复用/新建，返回 200 和新 ID；若清扫先发生则同一请求返回 409，行为取决于清扫时序。修复前真实 PGlite 回归输出 `marks_integration_test.go:288: expired replay = <nil>, want ErrDeleted`。

**修复。** `server/internal/marks/store.go` 在命中请求映射时以 `accepted_at > now-retention` 判定仍有效；恰好到期也直接返回 `marks.ErrDeleted`，HTTP 为 409，绝不进入 60 秒复用或新建分支。过期映射保留到分钟清扫，由删除触发器为原键写入墓碑，因此清扫前后重放都稳定返回 409。

**回归。** `marks_integration_test.go` 用确定时钟创建恰好到期的标记：服务层必须返回 `ErrDeleted`，HTTP 必须为 409/`retryable=false`，清扫前 `manual_marks` 不得增加；清扫后再次重放仍为 409，真实行归零，原 request_id 的墓碑恰好 1 条。

### 2. 删除待办提交后跨过 180 天仍须可恢复

**反例。** 到期前 DELETE 已提交待办，但独立登记确认失败；登记恢复后、分钟清扫前重试时，旧实现因保留期过滤把仍真实存在的行当成 404。App 会把 404 当作删除完成并清除本机指针，实际记录和待办仍在。临时恢复旧条件的回归输出 `marks_integration_test.go:350: DELETE marks/...: HTTP 404 want 200`。

**修复。** `server/internal/service/marks_http.go` 的 `DeleteSource` 存在性检查只要求当前账号下精确 `manual_marks.id` 仍存在，不再以保留期过滤。已提交的精确待办可继续完成物理删除并生成墓碑；真正删除后的下一次请求仍为 404。

**回归。** `marks_integration_test.go` 覆盖：创建标记与 `pending_erasure` 待办，把 `accepted_at` 回拨 4320 小时（180 天），DELETE 必须返回 200、真实行必须删除，随后 DELETE 返回 404，原 request_id 墓碑必须存在。

### 3. 503 响应契约补齐

`docs/api/app.yaml` 新增 `E503ServiceUnavailable` 响应组件，固定 `code: service_unavailable`、`retryable: true`，并为 `refreshTokens`、`listMarks`、`createMark`、`editMark`、`deleteMark` 以及支付六 operation（`getPurchaseToken`、`createOrder`、`restorePurchase`、三个支付通知回调）声明 503。`scripts/check_contracts.py` 对上述 11 个 operation 断言组件引用、错误码与可重试性，避免实现已返回 503 而 OpenAPI 再次漏记。审核故障仍使用 `E503`/`moderation_unavailable`，不能用 `E503ServiceUnavailable` 替换。

### 保留的数据与安全边界

- 墓碑仍只有 `(user_id, request_id)`，不保存标记内容、对象、场景、时间、密文或删除历史；账号删除级联清零。
- 删除仍在 `WithSession` 账号锁内复核会话，并只允许恢复精确源 ID 的待办；其他 pending 或 ledger 屏障继续 fail-closed 为 503。
- `privacy.ErrHidden` 仍只映射为可重试 503；只有 `accounts.IsAuth` 映射为 401，不会误清会话或本机加密草稿。
- 到期逻辑删除、导出过滤、分钟物理清理、关系人级联、跨账号隔离及免费额度边界均保持原有行为。
