本卡在本地 D13/T35 后继 `b5c89f05e2886df4ca6bdbabadac254e5736caa4` 上接入 T34 发布工具。命令、资源、日常备份与告警、生产封锁和外部前置条件见[运行手册](../../infra/t34/README.md)。该基线的 52 个 SQL 迁移与历史 T34 前版的 48 个 SQL 迁移不兼容。

## 本地部署与回退

1. 在干净 clone 中准备一个独占 Linux Docker daemon 和本地合成数据。按运行手册指定完整的 `T34_PREVIOUS_COMMIT` 与 checkout 外的 `T34_DECODER_APPROVALS`。审批必须匹配本次计算的候选和前版工件及 decoder 身份。
2. 执行 `infra/t34/accept.sh --config-only`。标准入口从 Git 白名单物化候选与前版，先跑归档测试，再验证 schema、运行时组合和审批，最终检查测试和闭锁生产的 Compose 配置。
3. 在同一个独占引擎执行 `infra/t34/accept.sh`，核对实际运行的 API/Web 镜像 ID、回环健康检查、备份及删除登记的恢复门禁。临时验收用 A → B → A → B 验证同 schema 镜像切换。出现 schema 差异时停止自动回退，并另行评估前向处理或恢复方案。
4. 固定 staging 的更新还要核对实际在位对象在当前审批索引中的完整身份。回执中的 `previous_release` 和 `rollback.release` 要能追溯到同一个持久 `release` 和原镜像 ID。

## iOS Release 打包

入口为 `infra/t34/ios/package.py`，以 `--no-codesign` 构建请求产出 Release 候选，不签名、不上架、不部署、不访问产品服务。它固定从 checkout 的 `app/` 构建，强制使用项目锁定的 Flutter 3.38.10 / Dart 3.10.9 和正式 `app/lib/main.dart`，命令等价于 `flutter pub get --enforce-lockfile` 后执行 `flutter build ios --release --no-codesign --no-pub --target=lib/main.dart --dart-define=APP_ENDPOINT=<值>`。工作树不干净、Flutter/Dart 版本不符、传入的 `--expect-commit` 与 HEAD 不符时直接失败。

每次运行必须指定一个尚不存在的新输出目录。构建前，入口在构建锁内把默认位置 `app/build/ios/iphoneos/Runner.app` 已有的包移到本次运行工作区；构建返回后该路径必须由本次命令新生成，否则失败并恢复旧包。随后仍在锁内把新包移入本次独占工作区，并继续持锁到本次收件结束。后续调用只能改共享默认路径，不能改写本次已拥有的输入。旧默认包保留到本次收件/校验结束，失败时才恢复。因此自定义 build-dir、返回成功却无新包、或双调用交错都不会把别的包按本次提交出回执。构建锁覆盖构建到收件结束，同一 checkout 的并发打包会被拒绝，不能改写本次输入。

```sh
# 从仓库根目录执行；RUN 必须是新目录
RUN=build/t34/ios-package-$(date +%Y%m%d%H%M%S)
python3 infra/t34/ios/package.py --output-dir "$RUN" \
  --expect-commit "$(git rev-parse HEAD)"

# 收件：必须提供独立期望，不能只读 receipt
python3 infra/t34/ios/package.py --verify "$RUN" \
  --expect-commit "$(git rev-parse HEAD)" \
  --expect-version 0.1.0 \
  --expect-build 1 \
  --expect-sha256 "$EXPECTED_SHA256"
```

输出目录只含最终命名的 `Runner.app.zip` 与 `receipt.json`。ZIP 与 receipt 先以临时名写入本目录；只有 bundle 校验、归档、receipt 和可选的 `github-output` 全部成功后才改为最终名。上述任一步返回失败都删除整个本次新目录，不留下最终命名 ZIP/receipt，也不改动其他调用或用户已有文件。成功时命令不写 stdout，退出码 0 即表示本次收件完成；结果看输出目录中的 `Runner.app.zip` 与 `receipt.json`、`--verify` 的退出码，以及可选的 `github-output`。stdout 在启动时缺失、断管，或在收件后不可写，都不改变成功退出码。错误仍走 stderr；`github-output` 仍是硬性回滚步骤，不吞构建、收据、`github-output` 或上传错误。打包与 `--verify` 使用同一套 bundle 校验：Runner、`Frameworks/App.framework/App`、`Frameworks/Flutter.framework/Flutter`、`PlugIns/ReplyShare.appex/ReplyShare` 必须是 arm64 iOS 设备二进制且有执行位；App 二进制须含两个 Dart AOT snapshot 静态字节标记，这是字节串检查，不是导出表、真实加载或签名验证；必须含项目声明的 `flutter_assets/assets/contract_examples.json`。Runner/ReplyShare 的 bundle ID、可执行名、版本与 build number，以及分享扩展点、`DTPlatformName=iphoneos` 必须匹配仓内配置。模拟器平台、无执行位文件、断链/越界符号链接、特殊文件、带 `embedded.mobileprovision` 的包均被拒绝。

`receipt.json` 记录源提交完整 SHA、`app/pubspec.yaml` 的版本与 build number、bundle/extension ID、endpoint 值/类型/来源、Flutter、Dart、Xcode、macOS 与架构，以及归档的 SHA256 与字节数。`--verify` 重算 ZIP SHA256 与大小，并与 `--expect-sha256` 及 receipt 对照；`--expect-version`/`--expect-build` 与 receipt 及还原后 Runner/ReplyShare 两份 plist 对照；`--expect-commit` 只与 receipt 的源提交对照，bundle 不内嵌 commit。CI 同次作业中 commit 来自 `$GITHUB_SHA`，版本/build 来自打包步骤读出的 pubspec，SHA 来自本次归档；这证明同 run 内一致，不是独立外部锚，使用独立公布的 SHA256 才提供外部对照。校验不证明该提交在当前远端可达、endpoint 可连接、构建可复现、实际加载通过或产物已签名。

`--no-codesign` 是构建请求；入口只核对 Runner 不含 `embedded.mobileprovision`，并允许 SDK 内嵌的 vendor `_CodeSignature`。receipt 的 `signing_request`/limitations 记录构建意图，不声称实际签名状态，也不把无签名工件等同于签名、托管或商店验收。未 notarize、未上传商店。

维护者还原包（空目录由 `mktemp` 分配）：

```sh
RESTORE=$(mktemp -d)
ditto -x -k "$RUN/Runner.app.zip" "$RESTORE"
```

`ditto` 保留 Unix 模式与符号链接；不要用不还原这些元数据的 Python `zipfile.extractall()`。`--verify` 内部使用等价的受控还原，并对不安全条目失败。

### endpoint 来源与类型

`APP_ENDPOINT` 是编译期 Dart 常量，必须与正式客户端接受范围一致：`mock`，或无凭据的 https origin。origin 不得带路径（除 `/`）、query、fragment 或用户名/密码；端口须在 1–65535；占位 `example.*`、`localhost`、回环/未指定/保留地址及 `.invalid`/`.test`/`.local` 一律拒绝。未传参数且未设 `T34_IOS_APP_ENDPOINT` 时值为 `mock`，receipt 标为 `mock-sample`，该包只是离线示例候选，不得当作真实 release。HTTPS 类型只表示配置合规，不代表已连接或已验证真实服务。receipt 不含凭据。artifact 名保留 `mock-sample` 或 `https` 以便下载前区分。

### 手动作业

`.github/workflows/t34-ios-package.yml` 仅 `workflow_dispatch`，`contents: read`，在 `macos-26` 上用固定 SHA 的 action 和 Flutter 3.38.10 跑上述入口。作业为每次运行创建带 `run_id`/`run_attempt` 的独占输出目录，用 `$GITHUB_SHA` 和本次 pubspec 版本/build 及本次归档 SHA256 先执行 `--verify`，再上传且仅上传显式的 `Runner.app.zip` 与 `receipt.json`，`if-no-files-found: error`。缺产物、失败或不匹配不会作为成功 artifact 上传。作业不部署、不签名、不访问产品服务；托管 runner、checkout、依赖缓存与 artifact 存储属于作业自身基础设施。artifact 名为 `t34-ios-unsigned-candidate-<mock-sample|https>-<run_id>-<run_attempt>`；其中 `unsigned` 仅表示 `--no-codesign` 构建请求，不是签名或托管验收结论。

### 具名离线验证

```sh
cd <clone>
python3 -IB infra/t34/ios/test_package.py
```

`test_package.py` 只用合成普通文件、Mach-O 头部、plist 与临时目录，不调用 Flutter、Xcode、网络、签名或云。它覆盖：旧包隔离与“构建返回成功但无新包”拒绝、私有构建输入在后续双调用后不被改写、旧构建包保留到收件结束并在失败时恢复、输出目录独占与失败删除、`github-output` 写入失败不留最终命名产物、完整 bundle/plist/架构/AOT 静态标记/资源/扩展校验、正常链接与执行位的归档/还原、越界或绝对链接与无 Unix 元数据拒绝、外部 commit/版本/build/SHA 期望与 receipt 对照、篡改拒绝、真实进程在正常、断管、启动即无 stdout、收件后 stdout 不可写四种情形下的退出码及最终产物/旧构建包/构建归档次数（打包与 `--verify` 各一组），以及 workflow 的手动/只读/固定 SHA/新鲜目录/先验证后两文件上传契约。产物有效性由实际解包校验确认，不依赖 stdout 文案。真实本机构建、托管 workflow 运行、真实 AOT/引擎/扩展产物、签名、真机安装与商店审核均未由该测试证明。
