# T12 · 整场、复盘与单项评分

## 范围和入口

T12 是 Go 内部模块，不开 HTTP 路由，不持久化原文、发成长事件或操作余额。服务端以认证账号、原操作 ID 和已校验归属的活动构造 `scoring.New(router, scope)`，其中 `router` 来自 T10 `catalog.NewRouter(runtime.Data, stop)`。不要从客户端接收模型、提示词版本、评分源 ID 或角色序列。

| 入口（`server/internal/scoring`） | 评分对象 | 成功值 |
| --- | --- | --- |
| `ScoreSession(ctx, scene, turns, profile)` | 结束时一次性传入按存储顺序的整场 `[]scoring.Turn`；仅 `user` 发言编号 1、2…，`assistant` 仅作上下文 | `Outcome[Full]`：主导 mode、四项及总分、三个情绪维度、单轮改写及说明，可选 `target_turn` |
| `Score(ctx, scene, context, utterance, profile)` | `full_review`，只评 `utterance` 即“我当时怎么做”；背景和画像不另算用户轮次 | 同上 |
| `ScoreSkill(ctx, scene, turns, profile, target)` | `single_skill`，关卡声明的一个 `observation / feeling / need / request` | `Outcome[Progress]`：目标项、分数、反馈，服务端派生 `pass / retry_in_three_days / retry_now`。无总分、情绪或行为分 |

**种子。** `server/internal/scoring/seed.txt` 是 T11 的一个 `scoring` 草稿，不绑定任何模型。T11 每任务/模型只有一条发布指针，因此一个版本内明确分整场和单项两种输出契约；`assessment`、`target_item` 和修复指令 `retry` 由服务端填入。场景、画像、背景和有序发言封装为独立的 user JSON 数据，不能成为模板或 system 消息。种子发布步骤：在 `server/` 运行 `go run ./eval/scoring seed` 生成 T11 `POST /admin/v1/prompt-versions` 的完整请求体；项目管理员先比对已有版本，未导入才 POST，记录返回的版本 ID。按 T11 给每个准入的主/灰度/备用生成模型分别发布，保留历史指针供回滚。评测前关闭分流。不自动选模型、不带凭证访问后台、不以硬编码种子兜底。

**调用结果与结算。** T10 先审输入、再审完整输出；T12 先看 `Terminal`，再看错误，最后才读取 JSON。两个尝试共用 60 秒上限、相同操作 ID 和任务；只有格式错误才发一次新请求（含固定修复指令、不回显坏输出），重新经 T10/T11 选版和审核。已审核但连 JSON 对象都不是的评分响应是 `gateway.ErrObjectFormat`，不在 T10 当作服务故障切备用。普通供应商、配置、取消等错误不触发 T12 格式重试。

| 状态 | T19/T23 消费方式 |
| --- | --- |
| `success` | 仅此时有结果和成功 `CallID`。完整评分由源模块在 T04 账号锁事务中保存 `detail_enc`，并用 `gateway.LinkScoreTx(ctx, tx, user, callID, activity, sourceID)` 关联，不复制明细到 T10。`Full.Values()` 只含 8 个整数；T04 事件消费端从源重读。成功对练保留首条已存回复的扣次，不另扣评分费。单项只保存目标进度，不关联整场分、不发评分完成事件。 |
| `scoring_failed` | 无成功评分；合法操作的最终评分失败交 T06 `Failed`，未扣不扣，已扣按原日幂等退。无效调用参数是 `ErrInput`，不是成功操作。 |
| `safety` | 固定 `gateway.HelpMessage`，无评分或进度。对练净扣零、复盘不扣。 |
| `moderation_unavailable` | 独立可重试技术错误，接入方映射 503「服务暂不可用，可重试」；不发求助提示，不评分，净扣零。 |

调用方先检查终止状态，**即使同时返回 error** 也不得继续生成；若为 T10 Stop 收尾失败，须按原操作补偿。恢复、幂等保存、原日退款及主动退出均属 T06/T19/T23，不在评分函数中重做。回复助手不要调用本包。

## 验证命令及实际结果

只使用合成材料和进程内可控假服务。以下在 `af58a76dcbcb8c63cf6b3b36f236cb5c2e3c93d7` 的干净源码副本叠加本卡补丁复验；Go 1.26.11，未读取 `.env`。

| 验收项 | 命令 / 证据 |
| --- | --- |
| 整场、复盘、单项隔离 | `cd server && go test -race -count=1 ./internal/scoring ./eval/scoring`。检验交错轮次、复盘仅一条用户表达、声明目标校验、分档、单项拒收整场输出，及数值投影不含文字。 |
| 严格格式、一次重试 | 同上。逐层拒绝漏键、多键、重键、大小写别名、`null`、错类型和非法枚举；总分需是 0–100 整数，入界但和不符以四项和覆盖；80 个汉字可、81 不可，轮次 0/越界拒绝。覆盖第二次成功、第二次失败、服务失败不重试，两端终止均无成功 ID。 |
| 审核与扣次交界 | `cd server && go test -race -count=1 ./internal/gateway -run 'Test(ScoringFormatAfterReview\|ModeratedAttempts\|TerminalContracts\|RoutedJSONWireAndPrivateStats)$'`（正则中 `\|` 表示文档表格转义，shell 使用普通 `|`）。用 T10 假服务确认先审核后报格式错误、审核故障与危机不切备用；核对日志投影、终止回调及合成余额，不取代数据库账本验收。 |
| 基础、回归和草案 | 根目录 `python3 server/eval/verify_t12.py`（可用 `--go` 指定 Go 1.26）。逐条与规范比对 10 条基础样例和 2 份回归期望输出；另 20 条全标「待人工复核」，其中 **6 条多轮**。校验 T11 草稿、160 个不含答案的请求规格。#11 强制观察 0，#12 强制观察 15、改写第 2 次用户发言；每次都用生产解析器验 80 字。 |
| 评测器拒绝误报 | `TestMetrics / TestOfflineBatch / TestReviewerSidecar`：注入格式错误、错轮、方差/极差/均值越界、少跑/重跑、混版本及温度漂移；整批恒定假输出虽可解析，仍因回归、准确性和 20 条未复核而不能通过。不把这些构造数据算作真实模型成绩。 |

合并复验在只含已发布代码和本卡补丁的源码快照上运行：`python3 server/eval/verify_t12.py` 核对 10+2 条规范参照、20 条待复核草案（其中 6 条多轮），生成 160 个首轮请求规格，未调用模型。`cd server && go test -race -count=1 ./...`（无跳过）和 `go vet -tags integration ./...` 均通过。

## 未验证条件

**没有真实模型运行或人工复核结论。** 规范 12 条是仓库已有参照，不声称为本卡人工标注。新增 20 条的期望仅是草案。真实审核质量、模型稳定性、准确性和受控真人抽检均待项目方；本卡没有读取真实用户或部署/发布模型。

项目方在准入环境执行（下列命令从 `server/` 运行）：

1. `go run ./eval/scoring plan > plan.jsonl`。每条合成样例连续 5 次，共 160 条；同一固定模型部署修订、种子版本、temperature **0.2**。文件含 `case,run,seed_sha256,temperature,messages`，无期望分和账号 ID。`plan` 只渲染，不发网络请求。
2. 由项目方的受控运行器顺序消费计划，经过准入生成与审核服务。固定模型快照和提示词；若部署侧无法锁定或证明实际温度为 0.2，停止验收。不要把计划元数据当作实测设置，不能跳过审核或切换后谎报原模型。记录**第一次原始输出**而非业务重试后的成功结果；失败/审核终止用空 `output` 占原行，不补采、不删行。
3. 每条回执为一行 JSON，字段 `case`、`run` 为整数，`model` 为实际固定模型及修订标识，`prompt_version` 为实际版本标识，`seed_sha256` 为对应种子哈希，`temperature` 为实际数值，`output` 为原始 JSON **字符串**（不预解析、补键或抹掉重复键）。回执及证据仅在受控环境，不进入业务日志或仓库。`go run ./eval/scoring check < results.jsonl` 按序读取，缺/重/多行或模型版本冲突报错；默认 20 条待复核，不会放行。
4. 独立人工逐条复核 13–32，另存 `reviewed.jsonl`（不要复制草案并改标签）；每行仅 `case`、`label_status:"已人工复核"`、`expected:{mode,nvc,total,emotion}`，数组顺序同规范。审核人及变更证据由项目方在受控环境另存。`go run ./eval/scoring check reviewed.jsonl < results.jsonl`：格式必须 160/160；每条 NVC 五次**总体**标准差 ≤5，三个情绪维度各自极差 ≤1；NVC 均值与参照差 ≤10、各维度均值差 ≤1。程序可核对数值，不能认证人工身份、准入资质或代替语义审阅。人工另审主导 mode、引文、最差轮和改写质量。有项失败先调提示词的扣分例子，全批重跑，新批不要拼旧结果。
5. 上线后每月仅由项目方在受控环境抽检 50 条真实评分；只记录错误类型，另写全新的虚构对话作回归，不搬运原话、用户/评分源 ID 或关系人资料。
