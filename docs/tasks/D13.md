# D13 源系统到期清扫

## 事实边界

`chat_imports` 的到期时点是 `received_at + 24 小时`，等于该时点即满足删除条件。服务启动时扫一次，运行后由每分钟维护循环重扫；单次尝试的客户端时限为 10 秒，PostgreSQL 删除语句时限为 5 秒。锁或存储故障可能推迟行删除，数据库恢复后由后续维护或重启清扫。活动 ID 和幂等根保留。

到期的 `chat_imports` 行由源系统清扫。回复助手和关系人推断的新提交均不向该表写入原文。训练导出不查询该表。独立历史导入导出分区只返回本人未到期记录的 `activity_id`、`received_at` 与固定的 `content_unavailable: true`。SQL 行删除不保证物理页、WAL、备份或供应商侧副本被擦除，也不代表生产日志已排除原文。供应商留存、备份/WAL、恢复链、物理介质和 T35 正式导出/删除仍需外部证据。

## 治理与 Fineprint

- 24 小时只描述 `chat_imports` 行的到期条件，不描述物理擦除时限。
- 清扫是尽力执行并通过后续维护重试，不是保证 24 小时整点完成所有删除。
- 数据库行、逻辑副本、备份/WAL、供应商处理和物理介质是不同证据层，不得合并成一句“已删除”。

## 宿主验证

准备一次性空 PostgreSQL 17 数据库及两个独立的本地 Redis 8.2 实例。数据库用户须能执行仓库迁移。普通缓存用独立实例，删除登记用空实例的 DB 0，配置 `appendonly yes`、`appendfsync always`、`maxmemory-policy noeviction`、`no-appendfsync-on-rewrite no` 和 `aof-load-truncated no`。使用临时端口、目录和合成连接信息，验证后销毁这三套一次性存储。不要读取 `.env`，不要指向默认开发库、生产服务或真实凭据。

从仓库根目录显式导出三项连接变量，再运行 D13 专用入口：

```sh
export D13_DATABASE_URL='postgres://synthetic:synthetic@127.0.0.1:<pg-port>/postgres?sslmode=disable'
export D13_REDIS_URL='redis://127.0.0.1:<ordinary-redis-port>/0'
export D13_LEDGER_URL='redis://127.0.0.1:<ledger-redis-port>/0'
./server/tests/d13-integration.sh
```

脚本不提供默认 URL；缺任意一项或值为空即失败。主机必须直接写成数字回环 IP（`127.0.0.0/8` 或 `::1`），不接受需要解析的 `localhost` 或域名；三项都必须写明确端口。PostgreSQL 必须写非空测试用户、口令和一个明确的数据库名，Redis 必须写明确的 `/数据库序号`，删除登记还须为 DB 0，普通缓存与删除登记不得共用端口。Redis 查询参数、片段和多主机写法均拒绝。

PostgreSQL 只允许单个合法 `sslmode` 参数，供开发回环连接使用；`host`、`port`、`dbname`/`database`、`user`、`password`、`service` 等目标或凭据覆盖参数，以及重复参数，均 fail closed。校验入口使用产品同款 `pgxpool.ParseConfig` 和 `redis.ParseURL`，不会自行猜测驱动语义：最终解析出的主机、端口、数据库和凭据必须与 URL 明文结构一致；PostgreSQL 的 TLS/重试 fallback 也必须全部停在同一个回环端点，任何多主机或其它端点均拒绝。校验进程会清除所有继承的 `PG*` 变量并把 `PGPASSFILE` 指向空设备；入口脚本也会把该变量固定为归档内的空临时文件，避免环境或用户 `.pgpass` 改变目标。

可在不连接任何服务的合成检查中先验证目标：

```sh
./server/tests/d13-integration.sh --check-targets-only
```

该模式只做 URL 与驱动解析，不拨号；即使通过，也只证明目标地址边界成立，不证明 PostgreSQL/Redis 已启动或可用。真实运行时仍继承上述三项变量，固定使用合成配置和合成字段密钥，不读取真实凭据。

脚本顺序运行并解析 Go 测试 JSON：`TestChatImportCleanupProcess` 先在空库运行真实 API 完成迁移和登记绑定；随后 `TestChatImportsExpireAtBoundaryAndRetryAcrossPoolRestart`、`TestReplyLifecycle`、`TestProfileLifecycle`、`TestReplyContactRegrantBlocksPendingDispatchAndSave` 与 `TestProfileInferenceReviewRegressions` 复用同一套临时存储。每个精确用例必须出现 `PASS`；任意 `SKIP`、`FAIL`、缺少预期 `PASS` 或命令非零退出都会使整次验证失败。不得把 `SKIP` 当通过。

进程用例检查重启后过期行已删、未到期行和活动根保留。锁故障分支在表锁仍持有时检查 API 健康、过期行仍存在、启动删除已退出；释放锁后，同一进程的维护循环须删除该过期行。数据库生命周期测试覆盖微秒边界及失败后再试，回复测试覆盖普通用户重发同一请求后沿用原结果且无导入原文落库。


## 两个首次导入入口

| 入口 | 有效授权 | 用户操作 |
| --- | --- | --- |
| 回复助手 | `reply_chat_import` / `2026-11-reply`。选择关系人时另需 `contacts` / `2026-11` 和可用名额。 | 「同意本次说明」保存授权。「开始分析」才提交聊天文字、可选目的及关系人关联。 |
| 关系人手记 | `chat_import` / `2026-11` 和 `contacts` / `2026-11`。 | 「同意并继续」保存授权并打开表单。「提交片段」才提交正文。 |

在「隐私与个人数据」的「聊天导入授权」中可以分别撤回，或前往原入口阅读告知后重授。旧版决定可在这里撤回。现有聊天推断表单的提示勾选用于确认分享范围，后端仍逐请求验证两笔关系人授权。

回复审核 503 和处理中 202 可显式重试原键。服务确认未完成回复绑定的原授权失效时返回 `403 reply_consent_expired`、`retryable: false`，页面保留草稿，下一次点击才生成新键。已完成回复在同账号使用相同请求键和输入时直接回放已存结果，计费保持一次。另一账号的同键属于该账号自己的请求空间。提交期间如果名册刷新移除了所选关系人，或提交预检发现该关系人已不可用，页面保留草稿并关闭分析按钮。单纯编辑文字不能解除关系人门禁。重新选择或明确取消关联后，用户需要再次点击分析。

回复每次物理发送前（含一次 401 刷新重放）先读取同账号的授权决定，最后读取所选关系人的名册与使用权益。两用途通过授权列表取得 `decision_id`；同版本撤回重授会生成不同 UUID。一次提交固定正文、目的、关系人、请求键和决定 UUID，重放不更换报文。确认决定已替换、撤回或权限已下降时停止该次发送；已确认的守卫变更或服务明确返回旧绑定失效可清键，单纯读取失败不清键。名册/权益暂不可读，或两次 GET 都成功但快照互相不一致时，本次不发送，保留关系人、草稿和原键；首次预检无需改写正文，用户可直接再次点击，重新读取后再决定是否提交。重新确认或改选本身均不会发送。403 后重新检查授权的迟到结果不会覆盖较新的选择。

`POST /v1/replies` 的新键携带 `reply_consent_id`，关联关系人时另带 `contacts_consent_id`。客户端 GET 之间、授权读取之后以及最后一读到服务端事务之间仍不是原子的。服务端在建键与 Begin 的同一权威事务里校验账号、用途、版本、期望的两个决定 UUID 和联系人权益。若窗口内的换决定或降权在该事务检查时已生效，拒绝发生在活动/建键/扣次之前，不派发；已有键沿用持久绑定，已完成或安全终止仍可无派发回放。事务后发生的撤回仍由既有派发和保存检查处理。

关系人保留当前归档的材料 SHA-256、关系人归属、owner_id 和租约。处理中会复核原授权记录。客户端可在授权读取时拦截陈旧草稿而不发送正文。服务端直发缺授权请求返回 403，重授后相关在途旧键返回 409。已结算为 `retryable` 的请求仍可在当前授权下重试同一关系人和同一材料。同一授权下可以接替到期租约，迟到的旧 owner 无法外发或写回。在表单等待 202 或可重试的审核 503 后，用户再次点「重试原请求」时沿用原键。显示画像更新前会读回关系人和名额。

### 正式 Flutter 与双账本复跑

先使用「宿主验证」的一次性存储执行 `./server/tests/d13-integration.sh`。要求两种授权顺序均通过。`D13_STALE_REPLY_DECISION` 与 `D13_STALE_CONTACTS_DECISION` 还须证明旧决定的新键请求被拒绝，未派发、未增加扣次或预留。`D13_CONTACT_FIRST` 的回复请求数、净扣次和预留分别应为 `0→1`、`0→1`、`0→0`。`D13_REPLY_FIRST` 的推断请求数和原文源行数应为 `0→1`、`0→0`。

随后将 PG 和两个 Redis 换为另一套空实例，用数字回环端口替换占位符。在宿主已安装 `oapi-codegen v2.5.1` 且 Flutter 依赖可用时，从仓库根目录运行：

```bash
(cd app && flutter pub get --enforce-lockfile)
(cd app && flutter test --no-pub -r expanded test/replies test/contacts test/privacy)
(
  set -o pipefail
  cd server
  for api in app admin; do
    oapi-codegen -config "internal/api/$api/config.yaml" "../docs/api/$api.yaml" |
      diff -u "internal/api/$api/routes.gen.go" - || exit 1
  done
)
(
  for name in $(compgen -e); do
    case "$name" in PG*) unset "$name" ;; esac
  done
  export PGPASSFILE=/dev/null
  cd server
  GOTOOLCHAIN=go1.26.0 \
  D13_REPLY_PG_PORT='<pg-port>' \
  D13_REPLY_CACHE_PORT='<cache-port>' \
  D13_REPLY_LEDGER_PORT='<ledger-port>' \
  go test -tags 'integration d13flutter' -count=1 -timeout=5m -v \
    -run '^TestD13ReplyFlutter$' ./internal/service
)
```

回复需观测 `[503,503,403,200,200]`，账号页撤回和回复页重授均无分析请求，失效后下一次点击换新键，同键回放仍只扣一次。Flutter 关系人见证只统计实际发出的画像 POST，预期状态为 `[409,409,200]`，最后一次明确点击提交新键并读回同一人的更新画像。客户端察觉授权代际变化时只重新读取授权，陈旧草稿产生零画像 POST。严格服务端的 `TestProfileLifecycle` 另行直发撤权期间的旧键并断言 403。独立只读 PostgreSQL 事务须同时输出 `D13_LEDGER_STAGE:verified` 和 `D13_CONTACT_INFERENCE_STAGE:verified`。见证检查两类请求均绑定同一账号下正确用途与版本的授权记录、回复恰有一笔持久扣次且零在途预留、关系人恰有一条 `invalidated` 和一条 `complete` 且已清执行租约，以及零新增历史原文源行。若失败，先查看 `D13_FLUTTER_FIRST_EXCEPTION`，再结合 `D13_CONTACT_SUBMISSION` 定位。验证结束销毁临时存储。
